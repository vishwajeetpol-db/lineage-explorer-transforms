Section 01

System at a glance

BrickTrace is a native Databricks App: a FastAPI backend serving a React/Vite single-page app, running inside the workspace as an app service principal. It reads metadata and writes to exactly one place it owns.

The browser renders the lineage graph with React Flow laid out by ELK in a Web Worker. Every request goes over HTTPS to the FastAPI backend, which authenticates as the app's service principal via OAuth — no static tokens. From there the backend reaches four dependencies, and only four.

Three of them are read-only: Unity Catalog system tables queried through a SQL warehouse, the Foundation Model API for AI features, and the Workspace / Jobs / Pipelines REST APIs for producer source and run parameters. The fourth — an app-owned Delta schema — is the only thing BrickTrace ever writes to.

Design principle BrickTrace is a metadata reader. It queries Unity Catalog system tables and BROWSE metadata, and its only writes land in one dedicated app-owned schema — so it clears security review quickly and can be shared workspace-wide.
Section 02

The lineage trace

Pick any table and BrickTrace renders its complete lineage cone — every upstream source back to every downstream target — across all catalogs and schemas, with the mediating jobs and pipelines in between.

The trace is a directional breadth-first walk over system.access.table_lineage from the seed table. The direction is the subtle part: ancestors are found by following target → source only, and descendants by following source → target only. A bidirectional walk would fan out through shared source tables (a raw samples.tpch.orders read by dozens of unrelated pipelines) and pull in every sibling consumer. Keeping each direction pure confines the trace to the seed's own cone.

The walk is metastore-wide — it crosses catalog and schema boundaries freely — and stops at a node cap with a truncation guard so a pathological graph can't run away. Complete traces are cached (see §7).

Section 03

From rows to a graph — routing vs precise pairs

Each system.access.table_lineage row is one real dependency: a (source_table, target_table, entity) triple. _build_graph_from_rows turns those rows into two distinct edge sets — and keeping them distinct is what makes the graph both readable and correct.

For display, edges are entity-routed: table → entity → table, so the job or pipeline that produced the dependency shows up as a hub node you can inspect for health and cost. But routing through a hub is lossy — it records that an entity read {A, B} and wrote {X, Y}, without recording which input actually fed which output.

So the backend also emits table_edges: the DISTINCT precise (source → target) pairs, taken straight from the rows. When the UI needs a datasets-only view, it renders these instead of trying to reconstruct dataset edges by collapsing the hub.

Design principle Never reconstruct what you already recorded. The entity-routed edges are for display; the precise table_edges are the source of truth for dataset-to-dataset flow.
Section 04

Transformation lineage — the differentiator

Unity Catalog records that "column A depends on column B." BrickTrace goes a layer deeper and reconstructs the actual SQL/PySpark expression that produced each column — casts, aggregates, CASE logic, window functions, CTE chains.

For a given column, a precedence resolver picks the best available source, most-trustworthy first. Deterministic, captured evidence wins; the LLM is the fallback, and a stored LLM answer is reused until the producer's source changes.

  1. precedence 1 · deterministicCaptured Spark plan

    If the producing pipeline ran with runtime plan capture on, the analyzed physical plan gives the exact per-column expression — no inference.

  2. precedence 2 · deterministicCaptured CDC spec

    For merge/CDC writers, the recorded change spec supplies the column mapping directly.

  3. precedence 3 · reusedStored LLM analysis version

    A previously computed analysis is served from the producer_analysis store and flagged stale when the producer's source hash no longer matches — so the UI can offer a one-click re-analyze.

  4. precedence 4 · freshFresh LLM analysis

    When nothing is stored, BrickTrace fetches the producer's source code and asks the Foundation Model to infer per-column transformations, then versions the result.

Fallback · deep framework analysis When direct analysis finds no column logic — a generic, metadata-driven ETL engine whose mappings live in config tables — an agentic streaming (NDJSON) second pass takes over: detect the config mechanism from the source, read the job/pipeline parameters, query the identified config table(s), and derive the per-column mappings, narrating each step as it goes. (backend/server/framework_analysis.py, POST /api/column-transformations/deep-analyze.)

The four heaviest panels — Impact, Root Cause, Governance, and Access — are persisted per (table, tab) in an app-owned capability_cache Delta table with a 24-hour TTL. Each shows a "cached · may be stale" badge and a refresh control that forces a live recompute, and admins can evict per entry, per table, or the whole cache from the ops dashboard.

Section 06

Business view & AI graph explanation

One underlying graph, two lenses. The Technical view is built for engineers; the Business view is a plain-language projection for everyone else — and it's a client-side, instant flip, not a second data fetch.

Business view relabels technical types to business terms (a job becomes a Process, a pipeline a Data pipeline, a table a Dataset), humanizes snake_case names into Title Case, shows a one-line plain-English description per dataset, and hides engineering detail — fully-qualified names, column-level edges, IDs, cost, and health. A sub-toggle chooses Data only (just the datasets and how they connect, drawn from the precise table_edges) or Data + processing (datasets plus the jobs and pipelines between them).

The AI "Explain this lineage" lightbulb sends the on-screen business-view graph to llm.explain_lineage_graph(), which returns a plain-English summary plus an ordered source → process → output walkthrough. Because the frontend posts what's visible, the explanation respects the current view — data-only or data-plus-processing.

Section 07

Performance & scale

Because BrickTrace only reads metadata, the warehouse is barely touched — and layered caching plus request coalescing keep it that way even at organization scale.

  • Request coalescing — many concurrent users asking for the same trace collapse to a single warehouse query; the rest wait on the same in-flight result.
  • In-process LRU + TTL cache — a memory-bounded cache in each replica serves hot traces without touching the warehouse.
  • Distributed Delta cache — a shared cache (applied via perf_patches.py) lets replicas reuse each other's completed traces across restarts.
  • Parallel BFS — the trace frontier is expanded concurrently across catalogs.
  • Versioned cache keys — the trace cache key is trace:v2:; bumping the version retires cached shapes when the response schema changes (as it did when table_edges was added), rather than serving stale structure.
Section 08

Security model

The security story is short by design: read metadata, write one schema, gate the dangerous switches.

  • Metadata-only. BrickTrace reads Unity Catalog system tables and BROWSE metadata. It never reads a row of your table data.
  • OAuth service principal. The app authenticates as its own service principal through the SDK — no static tokens are stored or required.
  • One write surface. All writes are confined to a single app-owned Delta schema (governance rules, producer analysis, DQ rules, notifications, caches). Your data catalogs are never written to.
  • Admin-gated operations. Live mode (cache bypass), the Control Panel's opt-in capabilities, and cache eviction require membership in ADMIN_GROUP_NAME.
  • Graceful degradation. When a system-table grant is missing, the affected panel stays empty and the diagnostics surface names the exact grant to add — the app never fails opaquely.
